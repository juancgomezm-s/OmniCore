## Cierre de filesystem.apply_patch y LSP

`filesystem.apply_patch` ya ofrece preview sin efectos y aplicación versionada
de hasta 64 archivos, con límites agregados, rutas del workspace, hunk exacto,
token de preview y preflight de todas las autorizaciones antes de escribir.
El Host verifica el manifiesto y los postimages, registra receipts pre/post por
archivo y clasifica una publicación parcial como `Unknown` para reconciliación;
no la repite automáticamente. La compensación entra en el historial usado por
`/undo`. El cache previo a autorización conserva sólo fingerprint acotado; las
imágenes completas se capturan después de autorizar.

`code.navigate` y `code.diagnostics` consumen configuración exclusivamente de
User (`languageServers` en `settings.yaml`). Cada extensión tiene un servidor
sin ambigüedad. El modelo sólo elige archivo y operación; el comando/argv vienen
de esa configuración y los argumentos no pueden ejecutar archivos del
workspace. El Host usa un proceso persistente propio del Run/Lane, snapshot
read-only, Strong obligatorio, red denegada y entorno vacío. Comprueba trust,
configuración, huella de ejecutable/archivos de inicio y versión del documento;
limita JSON-RPC/UTF-8 y rechaza ediciones/comandos del servidor. Las ubicaciones
devueltas deben ser URI de archivo dentro del snapshot.

En Linux, los archivos runtime de un servidor .NET no se infieren ni se montan
por directorio: `dotnet exec` recibe rutas User explícitas `--runtimeconfig` y
`--depsfile` además del ensamblado. El código ya verifica la huella y declara
cada archivo de inicio permitido en solo lectura; no concede acceso implícito a
un árbol de runtime o paquetes.

La prueba de integración ejecutó el fixture JSON-RPC .NET por el catálogo
Host, ProcessSessionManager y launcher Strong de Windows. Verificó definition y
references, rechazo de URI fuera, documento obsoleto, cambio de configuración
y trust durante la solicitud, cancelación y limpieza del proceso. Otras pruebas
cubren framing UTF-8 multi-frame, diagnostics, símbolos, timeout, petición
`workspace/applyEdit`, config tipada y extensiones duplicadas. Esto valida el
puente Core con el fixture; no valida la configuración ni el comportamiento de
un servidor LSP de producción instalado por Juan.

## Seguimiento de CI Linux e13

`dotnet <fixture.dll>`. La hipótesis es que bubblewrap, que monta sólo las rutas
de inicio declaradas, no expuso los `.runtimeconfig.json` y `.deps.json`
adyacentes. La prueba
ahora usa `dotnet exec --runtimeconfig <path> --depsfile <path> <fixture.dll>`;
esos tres assets entran por la lista existente de argumentos de inicio, con
fingerprint y bind de solo lectura. No se modificó el launcher general ni se
instaló Ubuntu. Las fallas de stdout se traducen a códigos acotados (`process_exited`,
`invalid_header`, etc.); texto de excepción y rutas no se devuelven.

propuesta durable, y bloqueo de la recuperación de Undo cuando existían cambios
ajenos. Se corrigieron con verificación del journal de origen y recuperación
explícita de clasificación sin reintento de escrituras. Los casos negativos y sus
recorridos Host/TUI forman parte del foco final. Undo incorpora una vista textual
redactada y acotada de la compensación, además de las consecuencias por archivo.

independiente sin recompilar: **177 casos, 173 PASS, 0 FAIL, 4 SKIP**, 33.460 s.

limitación y los hashes/timestamps reales del directorio del runner: no se finge
