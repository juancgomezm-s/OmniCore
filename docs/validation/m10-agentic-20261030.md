## Controles y oráculos independientes

Cada caso tiene fuentes y tests iniciales fijados, test público inmutable y un
oráculo Node fuera del workspace que verifica comportamiento y preservación.
Un exit 0, un mensaje de éxito o una llamada a herramientas no sustituyen ese
oráculo. Se cubren exploración, bug simple/multiarchivo, fallo de build/test,
refactor, contexto, delegación, denegación, fallo de modelo y resume.

- Denegación: intento rechazado por política real; archivo protegido idéntico.
- Modelo: relay loopback con un único 503, destino HTTPS fijo; sin registrar
  headers, bodies ni credenciales. Core se recuperó; Pi no lo hizo.
- Resume: interrupción después de la primera escritura, otro proceso, misma
  Session y primer archivo preservado; segundo paso terminado. Sin sembrar journal.
- Delegación Core: workflow productivo Explore → Implement → Verify, tres
  resultados aceptados, binding de propietario/Verify y repositorio comprobados,
  verifier Node real y oráculo sobre el **worktree de implementación aceptado**.
  No se publica implícitamente al padre, que conserva su fuente original.
- Pi: CLI real mediante el RPC existente, extensión explícita de benchmark con
  archivos acotados y un hijo real por el mismo cliente; sin editar OmniCoder.

El oráculo inicial del harness esperaba erróneamente que la delegación publicara al
padre y emitiera un join genérico. Se conserva ese fallo original y se corrige la
lectura offline contra el resultado nativo aceptado. Runner y finalizador ahora
comparten la misma comprobación; cinco pruebas offline verifican binding correcto,
rechazo de aceptaciones ajenas, ausencia de Verify y repositorio/ruta cambiados.
No se cambió el resultado del agente ni el código funcional de M9 para aprobarlo.

## Composición y defectos corregidos

La v1.1 reutiliza recibos v1.0 de casos cuya entrada y baseline son idénticos;
repite contexto en ambos brazos con material realmente suministrado y delegación
Core con Verify nativo como único gate de ese workflow. La v1.0 y sus diagnósticos
se conservan. El finalizador exige coincidencia exacta de entradas actuales y bytes
Core/Pi; no se presenta la composición como una única tanda nueva. Los 16 DLL Core
permanecieron idénticos a la [imagen fijada](evidence/m10-agentic-20261030/acceptance-image.json)
antes/después, incluida reanudación. Sólo el helper público de entrada para contexto
se añadió sin sustituir Host/Engine/Models. La imagen contiene las dos correcciones
productivas siguientes sobre `6c90d4ee`:

1. El esquema/parser de `filesystem.apply_patch` admite el `previewToken` opcional
   o nulo emitido por el decoder al previsualizar. Aplicar conserva el token exacto
   requerido, versiones, autorización y límites; no se concede escritura al preview.
2. El runtime permite el batch vacío exclusivamente al preview sin efecto de esa
   herramienta concreta. Otros resolvers y toda publicación conservan batch no vacío.

Regresión C# focal Release: **48/48**, cero fallos/omisiones. Python offline:
**47/47**, incluyendo oráculos negativos y recibos. Driver Host compilado con cero
advertencias/errores; módulos Pi pasan `node --check`. La CI del árbol integrado
se acredita por el check del PR, separada del gate funcional del benchmark:
`newCiAcceptance:false` en el recibo no se reescribe como si el benchmark la midiera.
