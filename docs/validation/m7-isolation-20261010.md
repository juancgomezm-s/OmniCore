## Primer checkpoint (histórico)

Se construye el backend Git y una entrada CLI **de inspección**, sin mutaciones del workspace. El backend de provisioning se prepara para una posterior frontera autoritativa de command, permisos y journal; no se presenta como una Lane operativa ni se expone una creación manual que eluda esa frontera.

La fidelidad del snapshot exige no sustituir silenciosamente el estado del usuario por HEAD ni omitir archivos no ignorados. Las opciones todavía no construidas se rechazan mediante un resultado tipado. Secretos y topologías no soportadas se rechazan de forma explícita, antes de materializar un árbol nuevo. Hooks, fsmonitor y filtros definidos por un repo no pueden ejecutar procesos arbitrarios como efecto oculto del snapshot.

La limpieza verifica ownership, identidad y rutas físicas. Un worktree con cambios, una rama activa o commits nuevos se conserva si no existe una decisión explícita de descarte; las refs de snapshot se retienen. El barrido de retención de siete días y la adopción de huérfanos siguen pendientes. No se usa `git reset --hard`, `git clean` ni una eliminación recursiva de paths suministrados por el usuario.

### Verificación previa a la corrección final de policy (histórica)

La integración F2, F3, F4, F5 y F6 está conectada a los comandos y servicios de Host. La aplicación de una propuesta sigue detrás de autorización, policy, lease y Barrier durable; una salida de lane es una propuesta y necesita integración explícita. Implement/Verify comparte una vinculación durable sin cambiar el ownership del worktree original. Undo conserva la atribución y utiliza compensación nueva, no reescribe el journal. Cleanup/discard retiene snapshot antes de quitar el worktree; el cleanup integrado exige prueba completa y revalida la identidad, árbol y ausencia de consumidores.

El ejecutor Claude recibe herramientas y límites derivados de la policy efectiva. La invocación no puede representar grants de rutas ni ámbitos parciales: esos permisos fallan cerrados antes de iniciar proceso. Los intentos externos se reservan durablemente en un máximo de dos cuotas no reembolsables, con sesión exacta para resume; el costo que devuelve un resume se compara con el techo total del Task y la cuota de invocación se entrega a `--max-budget-usd`. Uso previo incierto no se acredita como conocido ni se usa para permitir un tercer despacho. El parser cuenta una vez el uso repetido por `message.id`, usa el output terminal y rechaza discrepancias; no expone texto de stderr/proveedor en eventos o diagnóstico. Esto sigue el [contrato oficial de seguimiento de costo y uso](https://code.claude.com/docs/en/agent-sdk/cost-tracking); el CLI instalado era 2.1.296. `total_cost_usd` es una estimación del CLI, no una factura.

Límites: cada batch de integración admite hasta 64 archivos, 2 MiB por pre/postimagen, 8 MiB de imágenes agregadas y 16 MiB de manifest protegido. Apply admite archivos regulares de texto fiel con modo `100644`; binarios, ejecutables/modos distintos, cambio de topología de directorios, symlinks/reparse points, transformaciones Git y rutas de secretos quedan rechazados o fuera del contrato. Los leases protegen frente a escritores coordinados por el mismo Host; procesos ajenos conservan la ventana externa documentada. La validación ejecutada es en Windows; Linux sigue diferido.
