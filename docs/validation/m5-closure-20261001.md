### 2.5 Bug real corregido — charset de `function.name` (Chat Completions y Responses)

**Hallazgo (solo con provider real):** toda petición con tools fallaba con HTTP 400. Journal
`turn.abandoned`:

```
provider ProviderError: {"message":"Validation: Function at index 0 has an invalid name:
\"user.ask\". Only a-z, A-Z, 0-9, underscores, and dashes are allowed.","type":"Bad Request","code":400}
```

Los tool ids canónicos de OmniCore usan punto (`filesystem.read`, `plan.propose`, `user.ask`, …), y ese
char no está permitido. Ningún fixture HTTP lo detectaba (usaban nombres sin punto).

**Corrección (`src/OmniCore.Models/ToolNameWireCodec.cs`, compartida):** codificación **biyectiva** en la
frontera de transporte:

| canónico | wire |
|---|---|
| `.` | `-` |
| `_` | `_u` |
| `-` | `_m` |

Se codifica al **salir** (definiciones de tool, `tool_choice` exacto y eco de tool_calls/`function_call`
del assistant) y se **decodifica** al **entrar** (JSON normal y SSE) antes de que el runtime lo vea. La
resolución de tool y su autorización siguen operando sobre el `ToolId` canónico (INV-013/ADR-0024): la
codificación no toca permisos ni el journal. Es inyectiva (tokens de 2 caracteres, sin ambigüedad) y no
depende del nombre del provider (INV-007). El `ProviderCallId` se conserva intacto.

**Alcance en la Responses API (verificado con fuente primaria; sin llamada real a OpenAI).** El OpenAPI
oficial (`openai/openai-openapi`, `Components/schemas/FunctionToolParam`) declara para el parámetro de
function tool: `pattern: ^[a-zA-Z0-9_-]+$`. La Chat Completions API documenta lo mismo en
`FunctionObject.name` ("Must be a-z, A-Z, 0-9, or contain underscores and dashes…"). La unión de request
`Tool → FunctionTool` no repite el patrón en su prosa (hueco de la especificación), así que la
codificación se aplica de forma conservadora y reversible: si el endpoint aceptara puntos, la
decodificación los restituye igualmente. `AnthropicMessagesProvider` **no** se toca: la Messages API
acepta los nombres canónicos.

**Tests añadidos (21 en total, ver §9):** salida de tools, `tool_choice` exacto y eco del assistant; entrada
por JSON normal y por SSE con argumentos partidos; round-trip e inyectividad del codec sobre punto, guion,
underscore y combinaciones que parecen tokens de escape; y `ProviderCallId`/`ToolId` preservados. La
respuesta `filesystem-read` se decodifica a `filesystem.read`.

**Verificación real:** tras la corrección, el mismo `omni ask` completó el turno:
`[herramienta] filesystem.read → correcto` · `── EndTurn · pasos 2 · tokens 2714`.

## 3. Área 2 — Registro, alias, router y escalación

**Determinista.** 30 tests focalizados:

- **Registro + alias** — `ModelRegistryAliasTests` (10): alias único por modelo, rechazo tipado de alias
  duplicado o que colisiona con otro id (`AmbiguousModelAliasException`) y de nombre desconocido
  (`UnknownModelException`), ambos con `LocalizedText`. Los alias vienen de `models.yaml`
  (`ModelAliasConfigTests`, 4).
- **Router puro** — `ModelRouterTests` (20): `ModelRouter.Select` consume **solo** `EffectiveModelProfile`
  + hechos declarados; rechaza por disponibilidad, contexto, capacidad, `LocalOnly`, política de escritura
  y preferencias; `NoRouteAvailableException` expone la lista completa de rechazos tipados. `PreferLocal`
  es estable y no rompe el orden de preferencia (`4e68237`).
- **Escalación** — `ModelRoutingHost.NextEscalation` (spec §73): la cadena de `models.yaml` se filtra por
  el **mismo** router (capacidad/contexto/política de escritura) y respeta el modo `auto|ask|deny`
  (por defecto `ask`, nunca silenciosa). Eventos `model.escalated` con codecs (`1d06bbd`).
- **Sin ampliación automática de permisos:** cambiar de modelo no cambia permisos. La escalación no crea
  grants ni eleva el perfil; el comportamiento por modelo sale de `EffectiveModelProfile` (INV-018).
- **Estado durable:** la política se persiste con revisión (`ModelPolicyStoreTests`,
  `ModelPolicyTests` 23) y la cualificación con revisión optimista (§4).

**Pendiente honesto:** el `RouteCandidate` expone precio pero el router **no** lo usa para elegir, y no
existe aún `SessionRoutingPolicy`/`BillingMode` que impida que una Session local acabe en una ruta de pago
sin consentimiento. Eso es **M5.5, ADR-0046** (fase B, bug B6), no M5; se reporta como dependencia, no se
reimplementa ni se oculta.

## 4. Área 3 — Cualificación `quick` (CLI → Host → store → `EffectiveModelProfile`)

**Determinista.** 78 tests en el área:

| Componente | Tests | Foco |
|---|---|---|
| `ModelQualificationCliTests` | 6 | CLI→Host→store; consentimiento `--yes`/TTY; recomendación no aplicada |
| `ModelQualificationHostTests` | 6 | store de perfil/traits; tope de costo; recomendación; perfil efectivo |
| `QualificationQuickSuiteTests` | 12 | 3 probes deterministas (`reading-basic`→"fox", `reasoning-arithmetic`→"42", `structured-output`→`{"status":"ok","count":1}`) |
| `ModelQualificationStoreTests` | 18 | revisión optimista, `MarkStale`, aislamiento por clave exacta |
| `ModelQualificationKeyTests` | 29 | clave canónica SHA-256 (provider/modelo/revisión/cuantización/backend/template/adapter/ToolMode) |
| `QualificationRecommenderTests` | 7 | categoría conservadora, `PatchOnly`/`ScopeCoder`, nunca `FullAgent` |

Requisitos del mandato y dónde se cumplen:

- **Identidad/provider/modelo/tokenizer** — `ModelQualificationKey` (§ADR-0007 §5). El contador de tokens
  se elige por **capacidad declarada** (`llamaCpp`/`ikLlama`), no por nombre (`OmniHost.cs:183-190`).
  *Parcial:* el camino CLI→Host deriva la clave de `providerId + modelId + ToolCallFormat + ToolMode`
  (`QualificationKeyFor`); los campos `modelRevision`/`quantization`/`chatTemplateHash` (el "tokenizer" de
  la clave) existen y están testados, pero **`models.yaml`/`ModelDefinition` no los transportan**, así que
  dos configuraciones que solo difieran en plantilla o revisión comparten clave hoy. Se reporta.
- **Mutación fiable** — `Upsert` con `profileRevision`; `Upsert_requires_current_revision_and_never_overwrites`,
  `MarkStale_requires_current_revision` → `ModelQualificationRevisionConflictException`.
- **Topes de gasto** — `QualificationConsent(explicitlyGiven, maxTotalCostUsd)` +
  `QualificationCostCapExceededException`; `Qualify_exceeding_cost_cap_throws_typed_error_and_nothing_persists`.
  Nada se persiste si la suite no pasa entera.
- **Cancelación** — `ProbeRunner.RunSuiteAsync` comprueba `IsCancellationRequested` entre probes y usa un
  token enlazado con el timeout por probe; distingue cancelación de usuario (propaga) de timeout
  (`ProbeTimeoutException`).
- **La categoría recomendada NO concede permisos** — `QualificationRecommender` produce una sugerencia
  visible; el Host **nunca** la aplica. Test: `Qualify_recommends_a_category_but_never_changes_the_operational_policy`
  y `Qualify_runs_the_quick_suite_over_the_runtime_provider_and_persists` (afirma
  `no se cambió ninguna política`). Aplicarla exige `omni model policy set` explícito.
- **Redacción de contenido** — `RedactionPolicy` en `ExplorerTurn` y `RedactJson`/`RedactSensitive` en la
  salida del CLI; los secretos nunca llegan al journal/artifacts (INV-016).
- **Calibración exacta/estimada** — `/tokenize` de llama.cpp alimenta `TokenEstimateCalibrator`
  (`TokenEstimateCalibratorTests`, 14); en NVIDIA el conteo es **estimado** y así se marca.
- **Status line** — `UsagePresentationTests` (7), `SessionUsageReporterTests` (6), `RateLimitQuotaParserTests`
  (22): precio (`$`/`≈`), cuota **solo observada** (`Reported`/`Stale`), y `—` cuando no se informa
  (ADR-0031). La ejecución real mostró `session 2.7k tok · ≈$0.0003 · —` (precio estimado, cuota
  desconocida, nunca inventada).

**Pendiente honesto:** la suite `quick` **no** mide `FileMutationReliability` (lo dice el propio
recomendador: *"la suite quick no mide mutaciones de archivos"*); solo la suite `full` (M10+) lo hará. La
lógica del recomendador para ese trait existe y está testada, pero no se alimenta en M5. La fila M5 del
roadmap lo agrupa; aquí queda registrado el matiz.

## 8. Pendientes y bloqueos (sin adornos)

1. **Responses/Anthropic reales** requieren credencial/consentimiento del usuario. No se simulan como cierre.
2. **Charset de `function.name` en Responses:** ya implementado en el boundary de transporte (§2.5) con
   evidencia del OpenAPI oficial, pero **sin llamada real a OpenAI**; la validación real sigue pendiente.
3. **Cualificación real** no ejecutada: el tope de peticiones reales era 4, se usaron 3 y **queda 1**; la
   suite `quick` sola consume 3. Insuficiente.
4. **Clave de cualificación incompleta en el camino CLI real:** `models.yaml` no transporta
   revisión/cuantización/`chatTemplateHash`.
5. **Histórico de costo incompleto bloquea la sesión:** un paso con costo desconocido impide turnos con
   tope posteriores (`uso histórico incompleto`). Candidato a bug.
6. **M5.5 (no M5):** precio en el router, `SessionRoutingPolicy`/`BillingMode`, estado opaco/`Continuation`,
   uso perdido al suspender, etc. (ADR-0046). Reportados como dependencia; **no** reimplementados aquí.

## 10. Conclusión

**M5 sigue abierto.** Esta auditoría interina deja verificado en su parte determinista (1132 tests) y
